# WP Smart Search

Поиск по записям и по индексированным ссылкам для WordPress: AJAX-поиск в
админке и REST API (Application Password) для внешних инструментов —
дедупликации, аудита источников, внутренних ссылок.

Версия 2.7.0. Требуется WordPress 7.0+, PHP 8.0+ (WordPress 7.0 не работает
на PHP ниже 7.4 — плагин требует 8.0).

## Установка

1. Скопировать каталог `wp-smart-search` в `wp-content/plugins/`.
2. Активировать плагин в разделе «Плагины».
3. Создать Application Password в профиле пользователя — он нужен для
   доступа к API.
4. Поиск в админке: «Записи» → «Умный поиск».

## Возможности

- Страница поиска разложена на вкладки «Поиск», «API», «Индексирование»
  (`?tab=api`, `?tab=index`); без JavaScript вкладки работают как обычные
  ссылки.
- Ajax-поиск по записям и меткам в админке.
- REST API для внешних инструментов: поиск по записям и по ссылкам
  (домен, хост, точный URL, текст анкора).
- Морфология: слова ищутся по основам, между словами — логическое И.
  «обход песочницы» находит «обходу песочницу».
- Индексация ссылок из контента: таблица `wss_links` обновляется при
  сохранении записи.
- Доиндексация из браузера: на вкладке «Индексирование» шаг за шагом, с
  прогресс-баром и кнопкой «Остановить»; лок общий с фоновой задачей, прогресс
  сохраняется на сервере.
- Проверка дубликатов перед публикацией: поиск охватывает опубликованные,
  запланированные, черновики и записи «на утверждении» всех авторов.
- Batch-поиск по ссылкам: до 50 запросов за один вызов.
- Обновление из GitHub через штатный механизм WordPress.
- Корректное удаление: `uninstall.php` убирает таблицу, опции и кэш.

## REST API

Базовый путь: `/wp-json/wss/v1`.

Полная документация по методам — на вкладке «API» страницы «Умный поиск»
в админке: параметры `/search`, тело и ответ `/links/batch`, поля `/me`,
лимиты и таблица кодов ошибок.

Аутентификация — только заголовок `Authorization: Basic …` с
[Application Password](https://wordpress.org/documentation/article/application-passwords/).
Cookie-аутентификация для этих маршрутов не поддерживается. Минимальная
роль — та, у которой есть `publish_posts` (Автор и выше).

```bash
curl -s -u "user:xxxx xxxx xxxx xxxx xxxx xxxx" \
  "https://example.com/wp-json/wss/v1/me"
```

### `GET|POST /wss/v1/search`

| Параметр | Описание |
|---|---|
| `q` | Запрос. Слова ищутся по основам, между словами — И. Максимум 5 слов, 200 символов. |
| `scope` | `posts` (по умолчанию), `links`, `all`. |
| `type` | `all`, `tags`, `posts` (для `scope=posts/all`). |
| `match` | `auto` (по умолчанию), `fuzzy`, `exact` (URL/ID записи). |
| `page`, `per_page` | Пагинация, `per_page` 1..50. |
| `statuses` | Статусы массивом или строкой. Неизвестный статус — 400. |
| `date_range` | `any`, `today`, `week`, `month`, `year`. |
| `date_from`, `date_to` | ISO-даты, включительно. |
| `author` | ID автора (учитывается только при `edit_others_posts`). |
| `post_type` | Тип записи, по умолчанию `post`. Неизвестный — 400. |
| `exclude`, `exclude_id` | ID для исключения (максимум 200). |
| `url`, `domain`, `host` | Фильтры для `scope=links`: точный URL после нормализации, домен (с поддоменами), точный хост. |
| `anchor` | Текст анкора для `scope=links`. |
| `anchor_match` | `words` (по умолчанию), `exact`, `substring`. `words` — по словам с морфологией: `ghostscript` находит «Ghostscript 10.05» и «ghostscript», но не «ghostscripting»; `substring` — прежнее поведение (`LIKE %…%`). В ответе `match_type` = `anchor_words` / `anchor_exact` / `anchor_substring`. |
| `anchor_kind` | `phrase`, `url`, `empty`, `unknown` (можно списком): ссылки с анкором-фразой, с адресом вместо текста, с пустым анкором. `unknown` — старые строки до переиндексации. |
| `post_id` | ID записи или массив (до 100): все ссылки этих записей, без поиска по домену/строке. Удалённая запись даёт пустой список, а не 400. |
| `fields` | Поля `links.items` через запятую: `post_id`, `title`, `permalink`, `status`, `post_type`, `url`, `host`, `domain`, `anchor`, `anchor_kind`, `context`, `match_type`. Всегда возвращаются `post_id` и `match_type`; неизвестное поле — 400 со списком допустимых. |
| `exact_total` | `false` — не считать `total` (экономит один `COUNT`). |

Не более **10 000** совпадений на запрос (`WSS_Config::MAX_MATCHED_POSTS`,
значение видно в `/me` как `max_matched_posts`): записи читаются из базы
порциями по 500 и сразу превращаются в элементы ответа, поэтому широкий запрос
не держит в памяти весь контент сайта. Когда предел достигнут, в
`posts.truncated` приходит `true`, `items` содержит первые 10 000, а `total`
остаётся точным — он считается отдельным `COUNT` (если `exact_total` не
отключён). Пагинация в этом случае покрывает только собранные 10 000. Флаг
означает «предел достигнут», поэтому при ровно 10 000 совпадениях он тоже
выставляется — сверяйте `total` с `max_matched_posts`.

Ответ:

```json
{
  "query": "обход песочницы",
  "scope": "posts",
  "meta": { "terms": ["обход", "песочниц"], "tokens": 2, "dropped_tokens": 0 },
  "posts": { "items": [], "total": 1, "truncated": false, "page": 1, "per_page": 10, "total_pages": 1 },
  "links": { "items": [], "total": 1, "total_exact": true, "page": 1, "per_page": 50, "has_more": false }
}
```

`meta.terms` — по каким основам реально искали,
`meta.dropped_tokens` — сколько слов отброшено лимитом в 5 слов.

### `POST /wss/v1/links/batch`

До 50 поисков за один вызов. Тело — JSON:

```json
{
  "domains": ["example.com", "example.org"],
  "hosts": [],
  "urls": [],
  "anchors": [],
  "per_page": 5,
  "statuses": ["publish"],
  "fields": "post_id,url,anchor"
}
```

Ответ: `{ "results": [ { "lookup": { "domain": "…" }, "items": [], "has_more": false } ], "meta": { "count": 2, "truncated": false } }`.
В batch-режиме `total` не считается (`total_exact: false`). Поля те же, что у
`/search` (`post_id`, `title`, `permalink`, `status`, `post_type`, `url`,
`host`, `domain`, `anchor`, `anchor_kind`, `context`, `match_type`);
`anchor_match` и `anchor_kind` принимаются так же, как в `/search`.

### `GET|POST /wss/v1/me`

Текущий пользователь, его права и лимиты API: `can_search`,
`can_filter_by_author`, `allowed_statuses`, `visibility_mode`,
`visible_statuses`, `private_scope`, `cache_backend`, `index`, `max_per_page`,
`max_matched_posts`, `max_words`, `batch_limit`, `link_fields`,
`plugin_version`.

`index` — здоровье индекса ссылок: `state` (`ready`, `refreshing`, `rebuilding`,
`partial`, `stale`, `empty`), `refreshing`, `rebuild_required` (синоним
`needs_rebuild`), `mode` (`refresh`/`rebuild`), `last_pass_at`,
`refresh_pending`, `posts_total`, `posts_processed`, `posts_with_links`,
`posts_without_links`, `links_total`, `links_written`, `links_per_post`,
`percent`, `generation`, `index_version` и состояние задачи (`done`, `cursor`,
`processed`, `errors`, `last_run`). Снимок счётчиков кэшируется на 10 минут и
сбрасывается при сохранении записи, старте и завершении пересборки; во время
прогона счётчики читаются живыми.

**Перед аудитом ссылок проверяйте `index.state` / `rebuild_required`.** Пока
`state` не `ready` и не `refreshing`, поиск по ссылкам отвечает «ничего не
найдено» на любой запрос — это не значит, что ссылок нет. `refreshing` —
индекс полный, идёт инкрементальный проход, доверять можно. `rebuilding` —
идёт полная пересборка, `partial` — брошена/не завершена, `stale` — старая
версия формата, `empty` — индекса нет.

`update` — диагностика обновления: `plugin_basename` (фактический basename
установленного плагина), `transient_entry` (есть ли запись в `update_plugins`),
`transient_key` (под каким ключом она лежит), `new_version`, `package`. Если в
админке висит бейдж «Обновления 1», а страница обновлений пуста, `transient_key`
не совпадёт с `plugin_basename` — запись осталась от старого ключа.

### `GET /wss/v1/index` и `POST /wss/v1/index/rebuild`

Только для `manage_options`. `GET /index` отдаёт тот же блок, что `/me.index`,
плюс `last_run` и `errors`, и ничего не меняет. `POST /index/rebuild` ставит
фоновую пересборку в очередь и сразу отвечает `accepted: true` (HTTP 202) — он
не ждёт окончания работы.

## Обновления

Плагин обновляется штатным механизмом WordPress из репозитория
[Gnoztis/WP-Smart-Search](https://github.com/Gnoztis/WP-Smart-Search):
берётся **максимальная** версия из GitHub Release и тегов (`vX.Y.Z` и `X.Y.Z`
равнозначны), архив — zipball или zip-ассет победившего источника.
Предрелизы (`-beta`) и четырёхчастные версии (`1.7.0.1`) не принимаются,
поэтому тег достаточно поставить — релиз создавать не обязательно.

Проверка кэшируется на 6 часов. Кнопка «Проверить обновления» в строке плагина
сбрасывает кэш и **игнорирует паузу после неудачной проверки**: явный клик
всегда делает запрос к GitHub. Неудачная проверка запоминается на 15 минут с
кодом и причиной (`403` — лимит GitHub API, `404` — репозиторий/тег не найдены,
`401`/`403` с остатком квоты — токен, сетевая ошибка), и это видно в строке
плагина и в предупреждении на странице «Плагины», а не только в `/me`.

Без токена GitHub разрешает 60 запросов в час на IP; если на одном хостинге
несколько плагинов с апдейтерами, лимит исчерпывается. Токен (публичный
репозиторий — достаточно прав на чтение) задаётся константой в `wp-config.php`
или фильтром `wss_github_token`; запросы с ним уходят только на домены GitHub,
а сам токен нигде не выводится — `/me` показывает лишь `token_configured`:

```php
// wp-config.php
define( 'WSS_GITHUB_TOKEN', 'github_pat_…' );
```

Ключ записи в `update_plugins` — фактический `plugin_basename()` главного
файла, поэтому обновление работает из любого каталога (`wp-smart-search/`,
`WP-Smart-Search/` и т. п.): распакованный архив переименовывается в имя
установленного каталога, а записи под старым ключом вычищаются. Состояние
проверки видно в `/me` в поле `update`: `last_error` (`code`, `reason`, `at`),
`next_retry_in`, `token_configured`, `transient_key`.

## Кэширование

Кэш работает на Redis через PHP-расширение `redis` (phpredis). Других
зависимостей нет: ни плагины объектного кэша, ни drop-in `object-cache.php`
не нужны и не используются.

1. Если расширение `redis` загружено и сервер отвечает — результаты поиска
   кэшируются в Redis. Адрес, порт, пароль и база задаются константами
   `WSS_REDIS_*` в `wp-config.php` или фильтром `wss_redis_config`.
2. Если расширения нет или Redis не отвечает — плагин работает без кэша.
   Ошибки кэша не влияют на поиск: он просто идёт в базу.

```php
// wp-config.php
define( 'WSS_REDIS_HOST', '127.0.0.1' );
define( 'WSS_REDIS_PORT', 6379 );
define( 'WSS_REDIS_PASSWORD', '' );
define( 'WSS_REDIS_DATABASE', 0 );
```

Транзиенты как кэш не используются: они пишутся в `wp_options` и стоят
дороже запроса, который должны экономить.

Доступность Redis проверяется по требованию — на первом обращении к кэшу
в запросе, и после сбоя не чаще раза в минуту (время ожидания подключения
0.2 с). Счётчики rate limit при недоступном Redis хранятся в транзиентах,
иначе лимит запросов исчез бы.

Активный бэкенд виден в ответе `/wss/v1/me` в поле `cache_backend`:
`redis` или `none`.

Ответы `/wss/v1/*` отдаются с `Cache-Control: no-store, no-cache,
must-revalidate, private` и `Vary: Authorization`: выдача зависит от
пользователя (черновики, приватные записи), поэтому обратный прокси не
должен её кэшировать и не должен отдавать ответ одного автора другому.

## Индекс ссылок

Поиск по ссылкам (`scope=links`) работает по таблице `wss_links`, которая
заполняется при сохранении записи. Поэтому записи, сохранённые до установки
плагина, в индекс не попадают, а удаление таблицы (деинсталляция, переезд,
восстановление базы) оставляет индекс пустым — поиск по ссылкам при этом
молча отвечает «ничего не найдено».

Плагин восстанавливает индекс сам:

- при активации и при обнаружении пустого индекса ставится задача пересборки;
- пересборка идёт батчами по 50 записей в фоне (WP-Cron), с курсором,
  блокировкой от параллельных запусков и бюджетом времени 20 с на запуск;
- прогресс и состояние видны в `/wss/v1/me` в поле `index`, а также на
  странице поиска в блоке «Индекс ссылок» — там же кнопка
  «Переиндексировать ссылки» (её видит только тот, у кого есть право на
  пересборку). Снимок счётчиков кэшируется на 10 минут, сами цифры
  показываются администратору;
- **два разных действия, а не одно**:
  - «Доиндексировать» — инкрементальный проход: индекс остаётся полным,
    `index_version` сохраняется, обрабатываются только записи с
    `post_modified_gmt > last_pass_at` и строки, ещё написанные в старом формате
    (`anchor_kind = 'unknown'`). Пока он идёт, состояние `refreshing` — аудиту
    можно доверять;
  - «Пересобрать заново» — полный проход с нуля (с подтверждением): курсор,
    `index_version` и счётчики сбрасываются, состояние `rebuilding`;
- **готовность считается по состоянию задачи** (`done` + `index_version`), а не
  по `COUNT` строк: у записи без внешних ссылок строк в индексе нет вообще, и
  раньше из-за этого завершённая пересборка навсегда выглядела неполной.
  В `/me.index` теперь есть `state` (`ready`, `refreshing`, `rebuilding`,
  `partial`, `stale`, `empty`), `refreshing`, `rebuild_required` (синоним
  `needs_rebuild` для клиентов 2.6.x), `mode`, `last_pass_at`,
  `refresh_pending`, `posts_total`, `posts_processed` (записи с `ID <= cursor`),
  `posts_with_links`, `posts_without_links`, `links_total`, `links_written`
  (строк за текущий прогон), `links_per_post` и `percent` (по пройденным
  записям, до 100%), а также `cron` (`next`, `last`, `disabled`),
  `browser_marker`, `missing` (ID, которые не удалось прочитать) и `batch`
  (текущий размер пакета). Во время прогона счётчики считаются по фактическим
  строкам, а не из кэша: иначе устаревший снимок смешивался с живым прогрессом
  и показывал «0 ссылок, N пройдено, у N нет ссылок». Если `posts_processed > 0`,
  а `links_written = 0` — это симптом (таблица недоступна на запись или в
  записях нет ссылок), а не норма. Если обновлять нечего, «Доиндексировать»
  отвечает «Индекс актуален, обновлять нечего»;
- **внешний cron**: если на сайте `DISABLE_WP_CRON`, это нормальный режим —
  пересборку запускает внешний скрипт, дергающий `wp-cron.php`. Поле
  `cron.disabled` в отчёте носит информационный характер и само по себе не
  ошибка. Предупреждение в админке появляется только когда задача не завершена
  **и** следующего запуска нет в расписании (`cron.next = 0`) — это оборванная
  цепочка;
- ручной запуск — операция уровня сайта: по умолчанию требуется
  `manage_options`, право переопределяется фильтром `wss_rebuild_capability`:

  ```php
  // Отдать переиндексацию редакторам.
  add_filter( 'wss_rebuild_capability', static fn() => 'edit_others_posts' );
  ```

  Автоматическая пересборка (активация, обнаружение пустого индекса) работает
  без пользователя и проверки права не требует.

Если WP-Cron на хостинге не работает или батч идёт слишком долго, пересборку
можно провести из браузера: кнопки «Доиндексировать» и «Пересобрать заново» на
вкладке «Индексирование» отправляют по одному батчу за запрос (`admin-ajax.php`,
экшен `wss_index_step`, nonce + то же право), показывают прогресс-бар
«Обработано N из M (P%)» и кнопки «Остановить» и «Пересобрать заново». Пока вкладка
работает, браузер — единственный водитель: он пишет маркер на 5 минут, и
WP-Cron на это время не ставит задачи и не берёт работу. «Остановить» снимает
маркер (cron снова свободен), курсор при этом сохраняется, поэтому следующее
нажатие продолжит с того же места, а «Начать заново» (с подтверждением) сбросит
его в ноль.

Каждый браузерный шаг ограничен **бюджетом 15 секунд**: если батч не успевает,
шаг останавливается сам, возвращает `partial: true` и уже сделанное, поэтому
запрос не упирается в PHP/gateway timeout и не теряет прогресс. После такого
шага размер батча уменьшается (50 → 20 → 10) и запоминается в состоянии
задачи, чтобы следующие шаги были быстрее. Ошибка сети или 500 повторяется до
трёх раз с паузами 2/4/8 секунд, затем цикл останавливается с сохранением
прогресса и показывает код ответа.

Заброшенную задачу никто не оставляет: пока прогон не завершён, каждый шаг
держит в расписании **один запасной cron-событие** через `RUNNER_TTL + 60`
(пять минут маркера плюс минута). Пока браузер жив, `run()` на это событие
ничего не делает и лишь переставляет его; если вкладку закрыли — задача сама
продолжится примерно через шесть минут. При скрытии вкладки или уходе со
страницы скрипт снимает маркер через `navigator.sendBeacon` (запасной вариант —
`fetch` с `keepalive`), чтобы cron подхватил работу сразу, не дожидаясь TTL. На
`admin_init` плагин сам лечит забытую задачу: если `done = false`, события в
расписании нет и браузер не активен — событие ставится. Предупреждение в
админке остаётся только для случая, когда планирование действительно
заблокировано (например, фильтром `pre_schedule_event`) — с инструкцией, как
запустить вручную.

Две вкладки не дублируют работу: курсор двигается через
`UPDATE … WHERE option_value = <старый>`, поэтому шаг выигрывает только одна
вкладка, вторая получает отказ и продолжает со свежего курсора.

Старые ссылки с анкором-адресом (`<a href="https://x/y">https://x/y</a>`) в
индекс попадают: у них `anchor_kind = url`, найти их можно фильтром
`anchor_kind=url`. Строки, проиндексированные до 2.6.0, имеют
`anchor_kind = unknown` — их заполнит ближайшая полная пересборка (состояние
`stale` в `/me.index`).

Полная пересборка из консоли — самый надёжный путь для большого сайта: нет
браузера, нет WP-Cron и нет лимита времени на запрос.

```bash
wp wss index status
wp wss index refresh --batch-size=200
wp wss index rebuild --continue --batch-size=200
wp wss index rebuild --fresh
wp wss index rebuild --dry-run
wp wss index schema
wp wss index repair
wp wss index recreate --yes
wp wss index clear
```

`wp wss index status` печатает `state`, `posts_processed / posts_total`
(процент), `posts_with_links`, `posts_without_links`, `missing`, состояние
WP-Cron. `wp wss index refresh` — инкрементальный проход (только изменённые
записи, `index_version` сохраняется), `wp wss index rebuild` — полный проход без
флагов, `--continue` продолжает с сохранённого курсора, `--fresh` — явный сброс;
флаги `--continue`/`--fresh` взаимоисключающие. Команды печатают прогресс по
пакетам и завершаются с ненулевым кодом, если были ошибки.

### Схема таблицы

`/me.index.schema` (и вкладка «Индексирование») показывает фактическое
состояние таблицы: `state` (`ok`, `missing`, `outdated`, `broken`), `exists`,
`rows`, `stored_version`, `expected_version`, `columns`, `missing_columns`.
Проверяются реальные колонки, а не только опция версии: после обновления с
2.5.x таблица могла остаться без `anchor_kind`, и тогда поиск по ссылкам падает
или молча теряет строки.

- `wp wss index schema` — напечатать состояние схемы;
- `wp wss index repair` — `dbDelta` по текущей схеме **без потери строк**
  (добавляет недостающие колонки и индексы, если СУБД это позволяет);
- `wp wss index recreate` — удалить таблицу и создать заново по текущей схеме
  (то же, что кнопка «Пересоздать индекс» с подтверждением). После этого
  `state = empty`, пересборка сама не запускается — её нужно запустить вручную
  (`wp wss index rebuild` или кнопкой в браузере). В лог пишется одна строка:
  старая версия схемы, новая и сколько строк удалено;
- REST: `POST /wss/v1/index/recreate` с телом `{"confirm":"recreate"}`
  (без подтверждения — 400), только `manage_options`.

Повторный запуск безопасен: индексация одной записи идемпотентна (ссылки
обновляются, исчезнувшие удаляются), а незавершённая задача продолжается с
курсора, а не с нуля.

## Безопасность

- Запросы к БД — через `$wpdb->prepare()`, `LIKE`-значения — `esc_like()`.
- REST: `permission_callback`, обязательный заголовок `Authorization`,
  capability `publish_posts`.
- Видимость записей: пользователь с правом публикации видит опубликованные,
  запланированные, черновики и записи «на утверждении» всех авторов — это
  нужно для проверки дубликатов. Приватные записи (`private`) остаются
  автору и тем, у кого есть и `edit_others_posts`, и `read_private_posts`
  (редактор, администратор). Строгий режим («только опубликованное и своё»)
  включается константой `WSS_VISIBILITY_MODE = 'own'` в `wp-config.php` или
  фильтром `wss_visibility_mode`.
- CORS: строгий allowlist для `/wss/v1/*`; остальные маршруты REST
  обслуживает ядро WordPress.
- Переиндексация ссылок (кнопка на странице поиска) — отдельное право:
  `manage_options` по умолчанию, переопределяется фильтром
  `wss_rebuild_capability`; `/wss/v1/index` и `/wss/v1/index/rebuild` — только
  `manage_options`. Счётчики индекса видны в `/me` (агрегаты, без контента),
  сами записи по-прежнему подчиняются видимости.
- Пакет обновления принимается только по `https` и только с доменов GitHub.
- Секретов в коде нет; токен GitHub — константа или фильтр.
